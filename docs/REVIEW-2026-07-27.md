# Brokkr full-docs review findings (2026-07-27)

Working artifact from the 25-agent Diátaxis review (workflow wf_52547a72-dbf) plus a
cross-cutting auth-drift sweep, run after PRs #79/#80/#82/#83/#87. Not part of the
published book. Findings are code-verified by reviewer agents; re-verify citations when fixing.
Metis tickets BROKKR-T-0275..0295 index the actionable groups.

## Cluster verdicts

- The monitoring/fleet/health cluster is largely accurate at the code level — metric names, labels, buckets, the 6h hard retention ceiling, the 100 lines/sec log rate limit, WS subprotocol auth, sweep cadence, probe defaults, and the log-streaming annotation workflow all verify against source. Two real hazards remain: both the how-to and reference falsely present broker /readyz as a dependency-checking readiness probe (it is an unconditional 200, so DB outages are invisible to it), and the fleet docs predate PR #87 — they omit the cluster_name field and the ?pak_id tenant-scope filter, and still frame examples/ui-slim as the only UI when the broker now ships a supported Operator Console. A consumer can wire up correct Prometheus/probe/log-streaming setups from these docs, but will build an incomplete fleet consumer and a false sense of readiness gating.
- This cluster is unsafe as the sole guide for an external team: the multi-tenant Helm walkthrough leaves both tenant brokers running the publicly-known default admin PAK while its credential-capture step fails, and none of the four docs — including the security model — mention PR #87's ephemeral read-only admin UI token served to anyone who can reach port 3000, the GET /api/v1/paks tenant listing, or the cosmetic-only ?pak_id scoping. The hardening checklist also overstates isolation (unregistered agents still serve label/annotation-matched stacks) and omits the shipped-default-PAK override. The registration/enforcement semantics that were synced in PR #80 (no admin bypass, migration-23 backfill, precedence of generator-ID sources, audit retention) all verify against the code; the gaps are concentrated in everything that landed after that sync.
- The stack/template doc cluster is unusually accurate at the endpoint/payload level — routes, body shapes, status codes, error codes, label/annotation validation rules, the soft-delete trigger behavior, and the schema-defaults-not-injected nuance all match the code exactly. The one blocker is the explanation doc's versioning claim ('instantiation always uses the newest version'), which inverts the actual pin-by-exact-ID model and contradicts the reference and tutorial; two further major gaps (globally-unique stack names, and labels/annotations not carrying over to new template versions) will bite any external team in practice, and the unenforced template read-access on the instantiate path means the docs overstate tenant isolation. Fix the explanation doc's versioning bullet and add the two missing constraints and this cluster is fully consumable.
- These three docs were last synced before PR #87 and it shows: none of them mention the ephemeral read-only UI PAK credential class, the named-PAK tenant listing (GET /api/v1/paks), or the middleware's new bodyless 403s, and the error-code catalog is missing five live codes. Worse, two rotation/registration claims actively contradict the code — the 'restart the broker to rotate the admin PAK' path does nothing on an existing database, and the 'every agent is auto-registered with the system generator' claim is false for CLI-created agents — so a consumer following the admin-rotation or agent-scoping instructions can fail outright. The command/flag surfaces themselves (subcommands, flags, 409 semantics, cache TTL, audit wildcards) are accurate; the fixes needed are targeted, not a rewrite.
- The PR #80 doc sync holds up well for the registration-scope model: endpoint paths, auth rules, error codes, precedence order, Helm rendering, cascade semantics, and CLI apply behavior all verified against the code, so a consumer can follow the register/apply flows successfully. The two material problems are the unconditional claim that every agent is auto-registered with the system generator (false for broker-CLI-created agents, which silently miss fleet stacks) and the broken PUT /generators example in the reference (partial body fails deserialization, and created_at is not ignored). Post-#87 staleness is contained but real: reference/generators.md says nothing about GET /api/v1/paks or the ?pak_id tenant view filter, i.e. that generators now double as console tenant scopes.
- The health and diagnostics endpoint mechanics, defaults, and lifecycle are largely code-accurate (endpoints, statuses, retention_minutes 1-1440, cleanup 900s/1h, audit retention 90d, all five DB indexes verified), so a consumer can operate from these docs for the happy path. However, the diagnostics reference documents an events schema that does not exist (involved_object_kind/name vs the real involved_object) and both diagnostics docs describe a 'failed' status that is unreachable — collection errors arrive as 'completed' with an error payload, which will actively mislead troubleshooting. The audit docs are the stalest surface: PR #87's actor_name response field, the emitted agent.registered/deregistered actions, the best-effort (lossy) writer, and the fact that the zero-config console token can now read audit logs are all absent, undermining the docs' compliance and access-control claims.
- The pre-PR#87 material in this cluster is remarkably accurate — registration gating, soft-deletion triggers, webhook/work-order flows, fleet-legibility mechanics, and chart values all check out against code. The systemic failure is that PRs #82 and #87 landed with zero docs/src updates: no doc in the cluster mentions the embedded Operator Console, the ephemeral read-only UI PAK (a fourth credential class checked before all DB lookups), GET /api/v1/paks, or ?pak_id tenant scoping — and network-flows.md consequently misrepresents the security consequence of exposing port 3000 (anyone with network reach gets a read-only admin token). Two hard factual errors also need fixing: data-flows.md's 'agent events retained permanently' claim (default is 30-day hard deletion) and publishing-strategy.md listing already-shipped OCI Helm chart publishing as a future enhancement.
- The getting-started cluster is not safe for an external consumer to follow end-to-end: both Helm walkthroughs (installation.md Quick Start and evaluate.md Path B) produce a crashlooping agent because they omit broker.agentName/clusterName, installation.md never activates the agent so its test deployment can never reconcile, and its empty-pakHash guidance silently leaves the publicly-known dev admin PAK in place — a security-relevant falsehood. On top of that, PR #83 existing-Secret credential sourcing and the PR #82/#87 zero-config Operator Console are entirely absent from docs/src (only the chart READMEs know about them), the chart-based ConfigMap hot-reload story is not backed by code, and evaluate.md still pins v0.8.0 against a 0.8.4 lockstep release. configuration.md and getting-started/README.md are largely accurate; README.md's front-door quick start contains a request that 422s as written.
- This cluster is workable for the core install-and-deploy loop — the evaluate.md walkthroughs' API calls, registration gates, and admin-generator flow all check out against the code — but the Operator Console (shipped v0.8.3, extended in PR #87) is documented nowhere: no SUMMARY entry, no mention on the front page or in the components inventory, and evaluate.md still presents the retired ui-slim demo as the only UI while both eval paths silently serve the real console (with an auto-injected read-only admin token) on the same port 3000 users are told to expose. Combined with Path B pinning stale v0.8.0 charts, a consumer gets a materially outdated picture of what they are running and of its network-access security boundary.
- This cluster is not safe to follow as-is for a production install. Two blockers are actively misleading: both the broker chart README and network-configuration.md instruct enabling broker-terminated TLS that the binary does not implement (traffic stays plaintext), and no install path in the chart README covers the admin-PAK bootstrap, so documented installs run with a publicly known compiled-in admin credential. Beyond that, the agent README omits the default Tekton/Shipwright cluster-wide install and understates the Kubernetes floor (1.19 vs enforced 1.29), the image docs advertise SHA tags that CI never publishes plus a broken `ui`/`all` build command, and none of the network/image docs have been updated for the PR#82/#87 Operator Console (embedded in the broker image, exposed on port 3000 with network-access-as-auth). The environment-variables reference and install-operations how-to are largely accurate with only minor staleness.
- The navigation skeleton is structurally sound: SUMMARY.md is a perfect mirror of the docs/src tree in both directions (every listed page exists, every page is listed, including all 121 rustdoc stubs), and the one factual claim on these index pages (/swagger-ui and /docs/openapi.json) is code-verified correct. The weaknesses are index completeness, not broken links: the how-to landing hides the onboarding-critical agent-registration guide, the reference and explanation landings under-index their own sections, and — most materially for a consumer — the book's TOC has no entry anywhere for the v0.8.x Operator Console or the PR #83 existing-Secret install flows, so two shipped surfaces are invisible from the published book.
- The work-order, WS-protocol/internal-channel, shipwright, and reconciliation-troubleshooting docs are in good shape — nearly every constant, default, route, and lifecycle claim I traced (3/60/3600 defaults, 10s maintenance tick, lane capacities, backoff, deletion-marker trigger, annotation semantics, prune rules) is backed by code. The webhook docs are the weak spot: they document three behaviors with no backing implementation (event filters, 4xx non-retryable classification, the validate flag), misstate broker-side timeout and batch/hot-reload behavior, and omit the random-encryption-key restart hazard that can permanently kill all deliveries. A consumer can operate work orders, builds, and WS streams from these docs, but one wiring webhooks will be materially misled on filtering, retries, and key management until those sections are corrected.
- The onboarding docs are accurate and complete through PR #80 — day-zero generate-pak bootstrap, generator registration, PAK rotation, and multi-tenant schema setup are all correct and an external team can install and onboard following them. However, everything from PRs #82/#83/#87 is invisible: the Operator Console, the ephemeral read-only UI PAK (a security-relevant fact — network access to :3000 yields a read-only admin token), GET /api/v1/paks, ?pak_id tenant-scoped views, and the Helm existingSecret credential flows appear nowhere in docs/src, and the production install guidance still steers users to plaintext ConfigMap credentials. One published instruction is outright broken (root README stack-create example lacks the required generator_id) and one sample output (generate-pak's 'sha256:'-prefixed hash) would fail bootstrap validation if copied literally.
- Coverage is strong for everything through PR #80 — API route groups are ~93% documented (14 of 15 groups; only the new /paks group and ?pak_id scoping params are missing) and config/env key coverage in reference/environment-variables.md is effectively 100% (all Settings struct keys incl. watch_namespace and agent_events_retention_days). The consumer-blocking gaps are the three undocumented post-June changes: the Operator Console and its read-only UI-PAK security model (PR #82/#87) have zero pages, the Helm existing-Secret credential flows (PR #83) live only in chart READMEs, and network-configuration.md documents broker-side TLS that the binary does not implement — a cleartext-while-believing-encrypted hazard. An external team can install, onboard a tenant, and deploy from these docs, but will be surprised by the console (and its network-access-equals-read-only-admin boundary) and misled on TLS and the root README's first curl example.
- The four tutorial docs are in good shape on the post-PR#79/#80 registration model (opt-in gates, admin no-bypass, raw-YAML submission, rotate semantics all match the code), but the flagship first-deployment tutorial fails verbatim in two places: it never activates the INACTIVE dev agent (so no deployment is ever applied and Step 5's expected output cannot occur) and its deletion-marker cleanup example ('# deletion' comment body) is rejected with 400 by the broker's YAML validation. The activation gap silently propagates into cicd-generators.md, and multi-cluster-targeting.md's CLI-creation aside breaks its own targeting step because the broker CLI performs no generator registrations; an external team following these tutorials end-to-end would stall at first deployment until they discover the undocumented ACTIVE requirement.
- Not quite self-service. A new team can reach a working eval via evaluate.md Path B (the one flow that is complete and correct, including the agent-activation step the other paths omit), and generator/agent registration, deploy, and Prometheus monitoring docs are genuinely good. But the production onboarding path has real blockers: the canonical installation guide's verification silently fails (missing agent activation), its admin-PAK bootstrap advice is wrong for the chart (empty pakHash does not generate a fresh PAK), 'secrets handled properly' is only documented in the chart READMEs (never in the book, whose 0.8.0 version pins predate those features), and everything from PRs #82/#87 — the supported Operator Console, named PAKs, GET /auth/paks, tenant-scoped views — is entirely absent, so the team would have to contact the authors for production secret handling, UI access, and current tenant-scoping semantics.
- The SDK how-to cluster is unusually accurate — package names, versions, install commands, constructor options, apply/submit_manifests semantics, error and retry classification, and telemetry helpers all match the shipped 0.8.4 wrappers nearly line for line, with three real exceptions: the Rust retry example does not compile against retry's actual signature, the regeneration doc points contributors at the wrong spec file and omits the in-crate mirror from the commit checklist (a guaranteed CI failure path), and the Bearer-header claim is false for the Rust wrapper. The REST API reference page (docs/src/reference/api/README.md) is otherwise solid but has not been synced since PR #87: GET /paks, the ?pak_id= tenant-scope parameter, and the read-only UI PAK credential class are all live in the broker and the published OpenAPI spec yet absent from the doc. A consumer can install, authenticate, deploy, and operate from these docs; they would only be misled on the retry example, the regeneration workflow, and the PR #87 tenant-scoping surface.
- The learning path reads well sentence-by-sentence, but it has a hard functional break for newcomers: neither first-deployment.md nor installation.md's test flow ever activates the agent, and since agents are created INACTIVE and the agent binary skips all deployment work until activated (commands.rs:427), the flagship 'visible result' steps in both docs cannot succeed as written — evaluate.md is the only page that gets this right. Beyond that, the path silently forces external consumers into the contributor source-build environment for all tutorials, drops core jargon (stack/generator/deployment object) on the first page without a concepts link, and uses 'tenant' and 'generator' inconsistently across pages. Fix the two activation blockers and the tutorials-prerequisite misdirection first; the rest are polish.
- This is one of the most Diátaxis-disciplined doc sets I've reviewed: every lane is respected, pages self-declare scope, and cross-links consistently route procedures to how-tos, facts to reference, and rationale to explanation — no whole-section violations, hence no blockers. The two material issues for an external consumer are (1) the only Helm chart-values documentation living as reference tables inside the getting-started install guide, where a Reference-section reader will never find it, and (2) the hand-maintained API reference already drifting from code — PR #87's GET /api/v1/paks and the whole named-PAK/tenant-scoping surface are undocumented. The remaining findings are small findability/consistency fixes (index omissions, a shipped-vs-planned contradiction, a pinned stale version, contributor content nested in consumer how-tos).
